## 1. Мета, межі та терміни

### 1.1. Мета

Розробити REST API на Django REST Framework для створення й перегляду цікавих локацій, роботи з категоріями, відгуками, реакціями, рейтингом, популярністю, підписками й email-сповіщеннями. API має бути придатним для підключення окремого frontend-клієнта з інтерактивною мапою, але сам frontend до цього проєкту не входить.

### 1.2. У межах проєкту

- Django + Django REST Framework.
- PostgreSQL — основне постійне сховище.
- Redis — кеш, обмеження частоти обліку переглядів і брокер Celery.
- Сесійна автентифікація Django через cookies; JWT не використовується.
- Реєстрація, підтвердження email, вхід/вихід і скидання пароля.
- Категорії та локації з Soft Delete для локацій.
- Відгуки, історія редагувань через Soft Delete, Like/Dislike.
- Динамічні рейтинг і популярність, пошук, фільтри, сортування, пагінація.
- Redis-кешування списку локацій.
- JSON- і CSV-експорт; CSV обов'язково формується із застосуванням pandas.
- Email автору локації та активним підписникам після створення нового відгуку.
- Docker Compose для локального середовища, MailHog для локального приймання листів.
- Swagger/OpenAPI, API-, інтеграційні та інші автоматизовані тести, CI quality gates.

### 1.3. Поза межами

- Frontend, інтерактивна мапа в браузері та будь-які UI-компоненти.
- Геокодування адрес, перевірка адрес через сторонній сервіс і карти стороннього провайдера.
- OAuth/social login, JWT, мобільний клієнт.
- Модерація відгуків, скарги, антиспам-черги ручної модерації.
- Персоналізовані рекомендації, ML-модель популярності, вплив Like/Dislike на рейтинг або популярність.
- Навантажувальні/перформанс-тести як обов'язкова частина тестового завдання.
- Production-провайдер email, production-домени, секрети, сертифікати, конкретний хостинг та інфраструктура: таких даних поки немає. Production-конфігурація має бути підготовлена, але не містити вигаданих реальних значень.

### 1.4. Терміни

| Термін | Значення |
|---|---|
| Активна локація | Локація, у якої `deleted_at IS NULL`. |
| Soft Delete | Логічне видалення через встановлення `deleted_at`; рядок та пов'язані записи фізично не видаляються. |
| Активний відгук | Відгук, у якого `deleted_at IS NULL`. |
| Перегляд | Успішно оброблений запит до endpoint детальної активної локації, прийнятий обліком переглядів після перевірки годинного cooldown. |
| Рейтинг | Середнє значення `rating` усіх активних відгуків локації. Не зберігається як колонка. |
| Популярність | Динамічна числова оцінка 0–100 на базі середнього рейтингу, кількості активних відгуків за весь час і переглядів за останні сім днів. Не зберігається як колонка. |
| Авторизований користувач | Активний користувач із підтвердженою електронною адресою та дійсною Django-сесією. |
| Адміністратор API | Користувач з кастомною роллю `admin`. Роль визначає API-доступ і не виводиться лише з Django groups. |
| Підписка | Запис користувача про бажання отримувати сповіщення щодо локації. Підписка зберігається, коли локацію Soft Delete-ять. |

## 2. Принципи реалізації

1. **API versioning:** усі бізнес-ендпойнти першої версії розміщуються під `/api/v1/`. Маршрути, серіалізатори й HTTP-представлення версії ізольовані від доменної логіки, моделей і сервісів. Наступну версію можна додати через новий модуль `api/v2/`, не переписуючи логіку `v1` і не змінюючи поведінку чинних клієнтів.
2. **Тонкі views:** HTTP-рівень виконує автентифікацію, дозвіл, серіалізацію й виклик сервісів. Доменно значущі операції — наприклад редагування відгуку, Soft Delete, відновлення, облік перегляду та створення email-delivery — мають окрему сервісну/доменну логіку.
3. **ORM замість N+1:** агрегати локацій обчислюються SQL-виразами Django ORM. Для агрегатів над зв'язками, що можуть множити рядки (M2M categories, reviews, views), застосовуються окремі корельовані Subquery/OuterRef або еквівалентний перевірений підхід. Заборонено покладатися на Python-цикли з окремим запитом до кожної локації.
4. **Похідні значення не денормалізуються:** середній рейтинг, кількість активних відгуків, кількість переглядів за 7 днів, Like/Dislike totals і popularity не мають збережених агрегованих колонок. Зберігаються першоджерела — відгуки, голоси й події перегляду.
5. **Узгоджені транзакції:** складені зміни, що стосуються кількох рядків, виконуються атомарно. Кеш інвалідується після commit, а Celery-повідомлення не повинні відправлятися для транзакції, яка відкотилася.
6. **TDD:** нові правила спочатку описуються тестом. На вимогу Git workflow тест і наступна реалізація фіксуються окремими комітами.
7. **Жодних прихованих припущень:** наведені нижче числові межі та політики, які не задавалися початковим описом, є узгодженими технічними defaults для першої версії. Бізнес-зміни до них проходять через окрему зміну вимог і тестів.

### 3.3. Налаштування середовищ

- Спільні налаштування містяться у `base.py`; dev, test і production успадковують їх.
- `development`: локальний Docker Compose, DEBUG увімкнений, MailHog, зручна діагностика.
- `test`: ізольовані налаштування тестів, реальний PostgreSQL і Redis у CI; зовнішня доставка листів вимкнена/перехоплюється тестовим backend.
- `production`: `DEBUG=False`; потрібні секрети, `ALLOWED_HOSTS`, database/Redis/broker/email URLs задаються тільки середовищем; якщо обов'язкова змінна відсутня або небезпечна — запуск завершується з чіткою помилкою. Не зберігати справжні production values у Git.

- Стандартний локальний запуск — `docker compose up --build`; README при реалізації має описати первинні міграції та створення адміністратора.

## 4. Спільні правила API

### 4.1. Формат і versioning

- Усі бізнес-маршрути першої версії починаються з `/api/v1/`.
- Вхідні й вихідні бізнес-дані — JSON; CSV/JSON export має окремий режим завантаження файлу.
- Успішна відповідь колекції використовує пагінаційний envelope DRF: `count`, `next`, `previous`, `results`.
- Поля запитів і відповідей мають стабільні англомовні `snake_case` назви.
- Сервер сам задає `id`, `created_at`, `updated_at`, `created_by`, `deleted_at` та інші контрольовані сервером поля. Клієнт не може їх підміняти.
- Єдина політика доступу: невідомий об'єкт повертає `404`; існуючий активний публічний об'єкт, який користувач може читати, але не може змінювати, повертає `403`; Soft Deleted локація у звичайних list/detail endpoint повертає `404`. Deleted list повертає лише дозволений scope, а пряме restore чужої Soft Deleted локації повертає `404`, щоб не розкривати її існування. Власні subscription state ніколи не розкривають стан інших користувачів.

### 4.2. Уніфікований формат помилки

Усі помилки, які обробляє API exception handler, повинні мати стабільну структуру:

```json
{
  "error": {
    "code": "review_already_exists",
    "message": "An active review for this location already exists.",
    "details": null
  }
}
```

- `code` — стабільний машинний код у `snake_case`.
- `message` — коротке зрозуміле повідомлення англійською; тексти не містять traceback, SQL, секретів або внутрішніх шляхів.
- `details` — `null` або структуровані подробиці валідації, keyed за полями.
- `HTTP status` має відповідати типу помилки; `code` не замінює статус.
- Успішні відповіді не обгортаються в `error`.

Базові статуси: `200` — читання/успішна зміна з тілом; `201` — створення; `204` — успішна дія без тіла; `400` — помилкові поля/параметри; `401` — немає дійсної автентифікації; `403` — недостатньо прав; `404` — ресурс недоступний/не існує; `409` — конфлікт бізнес-правила або унікальності; `429` — перевищено rate limit; `500` — неочікувана внутрішня помилка без витоку деталей; `503` — лише якщо критична залежність не дозволяє виконати запит.

### 4.3. Автоматичні API-документи

- Swagger UI доступний у development за `/api/v1/docs/`; OpenAPI schema — `/api/v1/schema/`.
- OpenAPI описує authentication/cookie і CSRF-вимоги, ролі, параметри пошуку, сортування, пагінацію, формати експорту, коди помилок та приклади.
- У production доступ до Swagger/schema керується `API_DOCS_ENABLED`; за замовчуванням він вимкнений, доки оператор явно не дозволить його.

### 4.4. Основні зв'язки між сутностями

- `User 1:N Location` — одна локація має одного автора; користувач може створити багато локацій.
- `Location M:N Category` — локація має одну або більше категорій; категорія може бути пов'язана з багатьма локаціями.
- `Location 1:N Review` і `User 1:N Review`; унікальність стосується лише активного review на пару user/location, історичні Soft Deleted записи дозволені.
- `Review 1:N ReviewReaction`; одна реакція на користувача й відгук, тип реакції — like/dislike.
- `Location 1:N LocationView` — зберігаються події, а не сумарний лічильник.
- `Location 1:N LocationViewThrottle` на рівні identity: максимум один throttle row на location/hash identity.
- `Location 1:N LocationSubscription` та `User 1:N LocationSubscription`; одна пара user/location має один запис, який можна деактивувати й реактивувати.
- `Review 1:N EmailDelivery`; delivery пов'язується з конкретним адресатом-користувачем. Унікальність пари review/recipient запобігає повторному створенню логічної доставки.

### 4.5. Контракти запитів і відповідей

Приклади є нормативними за назвами полів і формою даних; ID, timestamps і обчислювані значення нижче ілюстративні.

**Реєстрація**

```http
POST /api/v1/auth/register/
Content-Type: application/json

{
  "username": "forest_walker",
  "email": "walker@example.com",
  "password": "a-strong-password"
}
```

```json
{
  "id": 42,
  "username": "forest_walker",
  "email": "walker@example.com",
  "role": "user",
  "email_verified": false
}
```

Реєстрація не входить у систему автоматично: користувач спочатку підтверджує email, після чого виконує login.

**Створення локації**

```http
POST /api/v1/locations/
Content-Type: application/json
Cookie: sessionid=...
X-CSRFToken: ...

{
  "name": "Riverside Cafe",
  "description": "A small cafe next to the river.",
  "category_ids": [1, 2],
  "address": "12 River Street",
```

## 5. Django app: `accounts` — користувачі й автентифікація

### 5.1. Модель користувача

Кастомна модель на базі `AbstractUser` створюється **до першої міграції застосунку**. Не використовувати стандартний `auth.User` для бізнес-зв'язків.

| Поле | Правила |
|---|---|
| `id` | Первинний ключ. |
| `username` | Обов'язковий, унікальний, після обрізання пробілів; максимальна довжина — 150 символів. |
| `email` | Обов'язковий, унікальний без урахування регістру; є ідентифікатором входу. Значення нормалізується в lowercase, а БД має functional unique constraint на `Lower(email)`; максимум 254 символи. |
| `password` | Лише стандартний Django password hash; ніколи не повертається в API і не логуються. Стандартні Django password validators увімкнені. |
| `role` | Кастомний enum: `user` або `admin`; публічна реєстрація завжди призначає `user`. Клієнт не може призначити чи змінити роль. |
| `email_verified` | Boolean, початково `false`, змінюється лише підтвердженням email або довіреною адміністративною операцією. |
| `is_active` | Стандартний Django-флаг; неактивний користувач не може автентифікуватися. |
| `is_staff`, `is_superuser` | Застосовуються для Django Admin за стандартною семантикою. API-права ґрунтуються на кастомній `role`; створення адміністратора має коректно налаштовувати потрібні Django flags. |
| `date_joined`, `last_login` | Стандартні серверні поля Django. |

Кастомний user manager і authentication backend повинні підтримувати вхід за email. Унікальність email повинна бути гарантована БД constraint-ом, а не тільки serializer validation. `createsuperuser`/адміністративне bootstrap-створення налаштовує `role=admin` і необхідні Django staff/superuser flags. Ролі не мають залежати від Django groups.

### 5.2. Функціональні вимоги

| ID | Вимога | Критерій приймання |
|---|---|---|
| FR-AUTH-01 | Реєстрація за username, email і паролем. | Успішна реєстрація створює звичайного користувача з `email_verified=false`; роль, active flags та серверні поля не можна задати в payload. |
| FR-AUTH-02 | Унікальність username та email. | Дублікат відхиляється з контрольованою помилкою; паралельні запити не створюють дублікати завдяки DB constraints. Email порівнюється case-insensitive. |
| FR-AUTH-03 | Підтвердження email. | На адресу надсилається обмежене в часі посилання/токен. Успішне підтвердження змінює `email_verified` на `true`; прострочений, неправильний або повторно використаний токен не дає підтвердити іншу адресу. Токен не є JWT. |
| FR-AUTH-04 | Повторне надсилання підтвердження. | Користувач може запросити нове підтвердження з rate limit. Відповідь не розкриває, чи існує довільна адреса. |
| FR-AUTH-05 | Вхід через email і пароль. | Успішний вхід створює Django session і встановлює cookie. Вхід за username не є контрактом API. Непідтверджений або неактивний обліковий запис не входить. |
| FR-AUTH-06 | Вихід. | Сесія знищується/інвалідовується сервером, cookie очищається; повторний запит не автентифікований. Endpoint вимагає коректного CSRF. |
| FR-AUTH-07 | Отримання поточного користувача. | `GET /auth/me/` повертає лише безпечні поля: `id`, `username`, `email`, `role`, `email_verified`, `date_joined`. Пароль і токени не повертаються. |
| FR-AUTH-08 | Скидання пароля. | Ініціація через email і підтвердження токеном/новим паролем використовують стандартний Django password reset mechanism і validators. Після успіху старий пароль перестає працювати. |
| FR-AUTH-09 | Захист від account enumeration. | Відповідь на password-reset і resend-confirmation не підтверджує, чи існує довільна адреса. Формат і статус зовні однакові для відомих/невідомих email. |
| FR-AUTH-10 | Керування строком життя сесії. | Строк задається змінною середовища `SESSION_COOKIE_AGE_SECONDS`; початковий default — 1 209 600 секунд (14 днів). Підтримується стандартна інвалідація Django session. |
| FR-AUTH-11 | CSRF для cookie/session auth. | Є endpoint отримання CSRF cookie/token; усі небезпечні запити з сесійною автентифікацією вимагають коректний CSRF token. Login endpoint також захищений від login-CSRF. |
| FR-AUTH-12 | Ролі. | Endpoint з правами адміністратора перевіряє кастомну роль `admin`. Роль `admin` не можна встановити через звичайну реєстрацію або звичайний профільний API. |

### 5.3. Endpoints

| Метод | Endpoint | Доступ | Призначення / результат |
|---|---|---|---|
| `GET` | `/api/v1/auth/csrf/` | Публічний | Встановити/оновити CSRF cookie і повернути токен для клієнта. |
| `POST` | `/api/v1/auth/register/` | Публічний | Створити користувача та поставити email-підтвердження в чергу. `201`. |
| `POST` | `/api/v1/auth/email/confirm/` | Публічний | Перевірити `uid` і токен, підтвердити адресу. |
| `POST` | `/api/v1/auth/email/resend/` | Публічний, throttled | Запросити повторне підтвердження; enumeration-safe response. |
| `POST` | `/api/v1/auth/login/` | Публічний, throttled + CSRF | Приймає `email`, `password`, повертає безпечний профіль і session cookie. |
| `POST` | `/api/v1/auth/logout/` | Автентифікований + CSRF | Завершити сесію. `204`. |
| `GET` | `/api/v1/auth/me/` | Автентифікований | Повернути поточного користувача. |
| `POST` | `/api/v1/auth/password/reset/` | Публічний, throttled | Ініціювати скидання пароля; відповідь не розкриває наявність email. |
| `POST` | `/api/v1/auth/password/reset/confirm/` | Публічний | Приймає ідентифікатор, token і новий пароль; завершити скидання. |

Поведінка токена підтвердження email: термін дії — 24 години, якщо інша величина не винесена в налаштування; токен криптографічно підписаний засобами Django, прив'язаний до облікового запису й адреси та одноразовий за результатом зміни стану. Password-reset timeout бере стандартне Django налаштування `PASSWORD_RESET_TIMEOUT` (початковий default Django — три дні, якщо не змінено конфігурацію).

### 5.4. Безпека сесій

- Сесії зберігаються у PostgreSQL через стандартний Django database session backend; не покладатися на Redis як єдине сховище сесій.
- `SESSION_COOKIE_HTTPONLY=True`, `SESSION_COOKIE_SAMESITE="Lax"`; `SESSION_COOKIE_SECURE=True` у production і false лише в локальному HTTP development.
- `CSRF_COOKIE_SECURE` відповідає режиму середовища. `CSRF_TRUSTED_ORIGINS` та `ALLOWED_HOSTS` беруться з environment; у production порожні/небезпечні значення мають блокувати старт.
- CORS не відкривається всім origins за замовчуванням. Frontend-origin буде явно додано, коли він стане відомий.
- Auth/password endpoints мають scoped rate limiting: рекомендований початковий baseline — login 10 спроб за хвилину з IP, password-reset 5 запитів за годину з IP, resend confirmation 3 запити за годину для IP/account. Ліміти конфігуровані та мають бути покриті тестами.
- Помилки входу не розрізняють «невірний пароль», «невідомий email», «email не підтверджено» і «обліковий запис неактивний» у спосіб, що дозволяє перебирати акаунти.

## 6. Django app: `categories` — категорії локацій

### 6.1. Модель

`Category`: `id`, `name`. Назва обов'язкова, обрізається від зовнішніх пробілів, має максимум 100 символів і є унікальною без урахування регістру. Не додавати опис, slug або зображення без окремої зміни вимог.

### 6.2. Функціональні вимоги

| ID | Вимога | Критерій приймання |
|---|---|---|
| FR-CAT-01 | Категорії доступні для читання. | Неавторизований користувач може отримати список і деталі категорій. |
| FR-CAT-02 | Створення/редагування/видалення — лише admin role. | Звичайний і анонімний користувач не може змінити категорію. Адміністратор може створювати та змінювати назву. |
| FR-CAT-03 | Початковий набір створюється data migration. | Після `migrate` набір наявний; повторний виклик migration у звичайному сценарії не створює дублікатів. |
| FR-CAT-04 | Назва унікальна case-insensitive. | `Cafe` і `cafe` не можуть одночасно існувати. БД забезпечує унікальність. |
| FR-CAT-05 | Категорію, що використовується будь-якою локацією, видаляти заборонено. | Перевіряються активні й Soft Deleted локації. Endpoint повертає `409 category_in_use`; категорія та зв'язки не змінюються. |
| FR-CAT-06 | Зміна категорій інвалідує cache списків локацій. | Rename категорії відбивається на списках/експорті після успішного commit. |

### 6.3. Початкові категорії

Data migration створює стартовий набір на кшталт: `Cafe`, `Coffee shop`, `Bar`, `Restaurant`, `Park`, `Museum`, `Gallery`, `Historical place`, `Nature`, `Entertainment`, `Shopping`, `Other`. Точні display names містяться в одній міграції; додавання нових початкових категорій оформлюється новою data migration, а не створенням під час запуску кожного web worker.

| `POST` | `/api/v1/categories/` | Admin | Створення. `201`. |
| `GET` | `/api/v1/categories/{id}/` | Публічний | Деталі. |

## 7. Django app: `locations` — локації, перегляди, пошук і експорт

### 7.1. Модель локації

`Location` містить:

| Поле | Тип / правила |
|---|---|
| `id` | Первинний ключ. |
| `name` | `CharField`, обов'язковий, максимум 150 символів; унікальність назви не встановлюється. |
| `description` | Обов'язковий `TextField`, не порожній, максимум 5 000 символів. |
| `categories` | Many-to-many до `Category`, клієнт має передати щонайменше одну активну категорію. Кілька категорій дозволено. |
| `address` | Обов'язковий рядок, максимум 255 символів; спеціальний формат або геокодування не перевіряється. |
| `latitude` | Decimal, 6 знаків після коми; діапазон `-90.000000..90.000000`. |
| `longitude` | Decimal, 6 знаків після коми; діапазон `-180.000000..180.000000`. |
| `created_by` | FK на кастомного user; задається сервером і не змінюється через API. |
| `created_at` | Серверний UTC timestamp, незмінний. |
| `updated_at` | Серверний UTC timestamp, оновлюється при зміні сутності. |
| `deleted_at` | `NULL` для активної локації, UTC timestamp для Soft Deleted. |

Не вводити унікальність комбінацій назва/адреса/автор. Після Soft Delete можна створити іншу локацію з тими самими даними. `Category` має захищений зв'язок: заборона видалення будь-якої категорії, яка використовується навіть видаленою локацією.

### 7.2. Дозволи та Soft Delete

| ID | Вимога | Критерій приймання |
|---|---|---|
| FR-LOC-01 | Публічне читання активних локацій. | Анонімний користувач може переглядати список і деталі активних локацій. Видалені не з'являються у звичайних endpoint. |
| FR-LOC-02 | Авторизовані користувачі можуть створювати локації. | Анонімний create не проходить. Автор призначається з `request.user`. |
| FR-LOC-03 | Кілька категорій, мінімум одна. | Create/update приймає масив category IDs; він не може бути порожнім. Неактивних/неіснуючих категорій не існує, а невідомий ID повертає помилку валідації. |
| FR-LOC-04 | Редагувати можуть автор або admin. | Інший звичайний користувач не може змінити дані. Поле `created_by` не переноситься. |
| FR-LOC-05 | Видаляти можуть автор або admin. | DELETE встановлює `deleted_at`, не видаляє фізично локацію і її пов'язані дані. Повторне delete не створює помилковий повторний ефект. |
| FR-LOC-06 | Перелік видалених локацій. | `GET /locations/deleted/`: admin бачить усі, звичайний авторизований користувач — лише власні; анонімний доступ заборонений. |
| FR-LOC-07 | Відновлення Soft Deleted локації. | Окремий restore action дозволений автору або admin. Встановлює `deleted_at=NULL`; автор, відгуки, реакції, перегляди й підписки зберігаються. |
| FR-LOC-08 | Відновлена локація знову публічна. | Вона повертається у звичайні списки й деталі. Підписки активних підписників знову можуть запускати листи. |
| FR-LOC-09 | Поля рейтингу/популярності динамічні. | Вони виводяться у відповіді API, але не мають денормалізованих колонок у Location. |
| FR-LOC-10 | Історія не каскадно знищується. | Soft Delete не видаляє відгуки, реакції, події переглядів чи підписки; після restore записи доступні згідно з власними статусами. |
| FR-LOC-11 | Стабільна пагінація. | Для однакових даних і параметрів результати мають детермінований порядок, включно з tie-breakers. |
| FR-LOC-12 | Дані зміни інвалідують list cache. | Create, update, soft delete, restore і зміна категорій після commit роблять попередні спискові cache keys недоступними. |

| `PUT` | `/api/v1/locations/{id}/subscription/` | Автентифікований | Створити/активувати підписку. Ідемпотентно. |
| `DELETE` | `/api/v1/locations/{id}/subscription/` | Автентифікований | Вимкнути підписку, зберігши її історичний запис. `204`. |

Endpoint-и `deleted/` і `restore/` мають бути оголошені так, щоб статичний маршрут `deleted/` не сприймався як `{id}`.

### 7.4. Обчислення рейтингу й популярності

#### Рейтинг

- `rating` — середній рейтинг **активних** відгуків локації за весь час.
- Значення округлюється до одного знака після коми у відповіді API.
- Якщо активних відгуків немає, `rating: null`.
- `review_count` — кількість активних відгуків за весь час. Це обчислюване поле, не збережений counter.
- Редагування відгуку, яке створює новий active review record, змінює поточний рейтинг і лічильник лише після успішної транзакції; старий Soft Deleted відгук в агрегати не входить.

#### Запропонована формула popularity

Формула є першою узгодженою технічною версією; усі коефіцієнти та constants мають бути зосереджені в одному модулі, покриті тестами та не розкидані по views/serializers.

Позначення:

- `R` — середній рейтинг активних відгуків, діапазон 1–5; якщо відгуків немає, використовувати `0` для формули.
- `N` — кількість активних відгуків за весь час.
- `V7` — кількість прийнятих переглядів за ковзні останні 7 діб від поточного часу UTC.

```text
rating_component  = R / 5
reviews_component = N / (N + 10)
views_component   = V7 / (V7 + 50)

popularity = round(
    100 * (
        0.50 * rating_component
      + 0.30 * reviews_component
      + 0.20 * views_component
    ),
    2,
)
```

- `popularity` у відповіді — число від `0.00` до `100.00`, округлене до двох знаків. Значення не зберігається у БД.
- `10` — saturation constant для кількості відгуків; `50` — saturation constant для переглядів за 7 днів. Вони не є бізнес-лімітами; це конфігураційні constants алгоритму.
- Кількість відгуків та рейтинг враховуються за весь час, лише перегляди обмежені останніми 7 днями.
- Like/Dislike не впливають на рейтинг або popularity.
- Популярність не нормалізується відносно інших локацій; дві бази з однаковими вхідними значеннями мають однаковий score.
- Усі три компоненти рахуються в SQL через Django ORM expressions/annotations, так що ними можна сортувати та фільтрувати без завантаження повного набору в Python.

#### Tie-breaking для сортування

- Значення `popularity` за замовчуванням сортується за спаданням.
- Якщо два значення популярності однакові: `rating DESC NULLS LAST`, `views_7d DESC`, `name ASC` (case-insensitive або нормалізоване сортування), потім `id ASC`.
- Для іншого вибраного primary ordering спочатку застосовується обраний primary field, а потім той самий детермінований tie-break chain без повторення primary field.
- `id ASC` — остаточний tie-breaker, щоб порядок не змінювався між запитами без змін даних.

### 7.5. Облік переглядів

- Рахувати тільки успішний `GET /api/v1/locations/{id}/` для активної, доступної локації. Невідомі ID, Soft Deleted location, `POST/PATCH/DELETE`, list, export і reviews endpoint не збільшують views.
- Для авторизованого користувача identity — стабільний user ID; для анонімного — Django session key. Для Redis ключів використовувати хеш identity, не зберігати email/username/session key у відкритому вигляді.
- Один identity може додати не більше одного перегляду конкретної локації за ковзні 60 хвилин. Інша локація має незалежний cooldown.
- Redis `SET NX EX` (або атомарний Lua/еквівалентний механізм) використовується для дешевого cooldown. Race condition не має призводити до подвійного запису в межах одного вікна.
- `LocationView` — durable event у PostgreSQL: `id`, `location`, `identity_hash`, `viewed_at`. Це **першоджерело подій**, а не збережений агрегований counter. Історія дає надійний sliding 7-day count навіть після перезапуску/очищення Redis.
- `LocationViewThrottle` — технічний рядок з унікальним `(location, identity_hash)` і `last_counted_at`. Він зберігає стан cooldown, але не агрегований лічильник переглядів. Значення identity — хеш, а не email, username або session key у відкритому вигляді.
- Алгоритм: Redis key — швидкий pre-check; при cache miss сервіс бере DB row lock для відповідної пари локація/identity, перевіряє `last_counted_at`, створює `LocationView` і оновлює cooldown у транзакції. Після commit Redis cooldown key записується з відповідним залишком TTL. Унікальний constraint і блокування рядка захищають одночасні перші запити.
- Якщо Redis недоступний, PostgreSQL row lock/cooldown залишається джерелом правильності й не дозволяє дублювати перегляди. Якщо запис події не вдався, не залишати cooldown key, який блокує законний повтор без наявної події. Проблеми tracking журналюються, але збій необов'язкової аналітики не повинен робити публічну деталь локації недоступною.
- Запис події відбувається після успішного проходження object lookup, permission checks і серіалізації відповіді деталей. `views_7d`/`popularity` у тілі цього самого detail response можуть представляти snapshot до поточного view event; наступні обчислення вже враховують подію. Немає окремої бізнес-фільтрації ботів/сканерів або додаткової heuristics.
- Усі concurrency сценарії (включно з Redis miss/відмовою, одночасним першим переглядом і помилкою DB insert) мають бути покриті integration tests.

### 7.6. Пошук, фільтрація, сортування й пагінація

#### Пошук

- Query parameter: `search`.
- Case-insensitive literal substring search у `name` **або** `description` (OR semantics), наприклад `search=river` знаходить назву/опис, у якому є `river`.
- Пошук не виконує зовнішнього геокодування, морфологічного аналізу або accent-folding.
- Максимальна довжина `search` — 100 символів; порожнє значення ігнорується, неправильні типи query parameters повертають контрольовану помилку.

#### Фільтри

| Параметр | Семантика |
|---|---|
| `category` | Ім'я категорії, case-insensitive exact match; дозволено повторювати параметр (`category=Cafe&category=Park`) — OR між зазначеними категоріями. |
| `author` | Точний username автора, case-insensitive. |
| `rating_min` | Нижня межа рейтингу включно, `1..5`. |
| `rating_max` | Верхня межа рейтингу включно, `1..5`. |
| `popularity_min` | Нижня межа популярності включно, `0..100`. |
| `popularity_max` | Верхня межа популярності включно, `0..100`. |

Одне передане значення рейтингу/популярності означає одну задану межу; передавання обох меж означає діапазон включно. Якщо обидві межі задані, нижня не може перевищувати верхню. Локації з `rating=null` не проходять рейтинг-фільтр, якщо задана хоча б одна rating boundary. При цьому для рейтинг-сортування вони розміщуються після numeric values (`NULLS LAST`).

#### Сортування

Query parameter: `ordering`. Дозволені тільки `created_at`, `rating`, `popularity` і префікс `-` для descending: `created_at`, `-created_at`, `rating`, `-rating`, `popularity`, `-popularity`. Невідоме поле сортування відхиляється або обробляється узгодженою стандартною помилкою `400 invalid_ordering`; не інтерпретується як ім'я довільної колонки. Default — `-popularity` із tie-break правилами вище.

#### Пагінація

- `PageNumberPagination`.
- Default `page_size=20`; клієнт може передати `page_size`; верхня межа — `100`.
- Параметри: `page`, `page_size`.
- Від'ємні, нульові там, де вони не дозволені, нечислові значення, `page_size > 100` або некоректні параметри повертають стандартизовану `400 invalid_pagination`; номер неіснуючої сторінки повертає `404`. Поведінку зафіксувати тестами.
- Експорт використовує ті ж пошук, фільтри та ordering, але ігнорує `page`/`page_size` і повертає всі відповідні активні результати.

### 7.7. JSON/CSV export

- `GET /api/v1/locations/export/?format=json` або `?format=csv`; за відсутності `format` — `400 unsupported_export_format` (не вгадувати формат неявно).
- Export використовує ті самі дозволені `search`, `category`, `author`, `rating_min/max`, `popularity_min/max`, `ordering`, що і list endpoint.
- Soft Deleted locations не включаються.
- `Content-Disposition: attachment` з filename `locations-YYYYMMDD.json` або `.csv`, дата у UTC.
- JSON містить масив об'єктів зі стабільним набором полів; CSV — header row та еквівалентні дані. Експорт не включає email, password-related fields або інші приватні дані автора.
- Поля експорту: `id`, `name`, `description`, `categories`, `address`, `latitude`, `longitude`, `author_username`, `created_at`, `updated_at`, `rating`, `review_count`, `views_7d`, `popularity`.
- JSON `categories` — масив назв. У CSV назви категорій мають визначене однозначне представлення (рекомендовано `|` delimiter всередині поля); CSV quoting/escaping виконується коректно.
- CSV формується **через pandas**. Щоб уникнути необхідності тримати весь великий експорт у пам'яті, дозволено обробляти query chunks і послідовно віддавати `DataFrame.to_csv()` chunks. Не створювати тимчасовий публічно доступний файл на диску.
- Некоректний формат повертає `400 unsupported_export_format`. Дані експорту не кешуються окремо за замовчуванням.

## 8. Django app: `reviews` — відгуки та реакції

### 8.1. Модель відгуку

`Review`: `id`, `location`, `author`, `rating`, `comment`, `created_at`, `updated_at`, `deleted_at`.

- `rating`: ціле `1..5`, обов'язкове.
- `comment`: необов'язковий, порожній рядок допускається, максимум 2 000 символів.
- `author`: задається тільки сервером.
- `location`: тільки активна локація для create/update.
- Підтримується історія: старі відгуки soft-deleted залишаються в БД.
- DB partial unique constraint гарантує максимум один відгук із `deleted_at IS NULL` на пару `(location, author)`. Application validation дає зрозуміле повідомлення, DB constraint захищає від конкурентних дублікатів.

### 8.2. Функціональні вимоги до відгуків

| ID | Вимога | Критерій приймання |
|---|---|---|
| FR-REV-01 | Перегляд активних відгуків. | Відгуки до активної локації публічні; Soft Deleted reviews не повертаються у list/detail. Список має пагінацію. |
| FR-REV-02 | Створення доступне лише після автентифікації. | Анонімний користувач отримує контрольовану помилку автентифікації. |
| FR-REV-03 | Один активний відгук на user/location. | Повторний POST, коли активний відгук уже є, повертає `409 review_already_exists`. Унікальність захищена БД. |
| FR-REV-04 | Дозволено відгук на власну локацію. | Система не забороняє self-review. |
| FR-REV-05 | Відгук можна редагувати автору. | PATCH/PUT soft-delete-ить старий запис і створює новий active record у межах однієї транзакції. Відповідь повертає новий активний review. Старий ID залишається історичним і більше не редагується. |
| FR-REV-06 | Видалення відгуку — Soft Delete. | Автор може DELETE власного активного відгуку; `deleted_at` заповнюється, дані та реакції зберігаються. Повторне видалення не створює нового стану. |
| FR-REV-07 | Доступ до зміни лише для автора. | Адміністратор не може редагувати чи видаляти чужий відгук лише через роль admin. Немає модераторських дій. |
| FR-REV-08 | Створювати/редагувати можна лише для активної локації. | Якщо локація Soft Deleted, create/update недоступні; історичні відгуки залишаються збереженими. |
| FR-REV-09 | Зміна набору активних відгуків оновлює похідні агрегати. | Після create/edit/delete рейтинг, review_count, popularity та list cache відповідають новому стану. |
| FR-REV-10 | Перегляд відгуку. | `GET /reviews/{id}/` повертає лише активний відгук; видалений/невідомий ID недоступний у публічному API. |

### 8.3. Endpoints відгуків

| Метод | Endpoint | Доступ | Призначення |
|---|---|---|---|
| `GET` | `/api/v1/locations/{location_id}/reviews/` | Публічний | Активні відгуки локації, пагінація. |
| `POST` | `/api/v1/locations/{location_id}/reviews/` | Автентифікований | Створити review з `rating` та optional `comment`; `201`. |
| `GET` | `/api/v1/reviews/{id}/` | Публічний | Деталі активного відгуку й live `likes_count`, `dislikes_count`. |
| `PUT/PATCH` | `/api/v1/reviews/{id}/` | Лише автор | Заміна як новий active review з Soft Delete попереднього, транзакційно. |
| `DELETE` | `/api/v1/reviews/{id}/` | Лише автор | Soft Delete, `204`. |
| `GET` | `/api/v1/reviews/{id}/reaction/` | Автентифікований | Стан поточної реакції користувача, `like`, `dislike` або `null`. |
| `PUT` | `/api/v1/reviews/{id}/reaction/` | Автентифікований | Встановити/замінити реакцію з body `{"type":"like"}` або `{"type":"dislike"}`. |
| `DELETE` | `/api/v1/reviews/{id}/reaction/` | Автентифікований | Видалити власну реакцію, `204`; idempotent. |

### 8.4. Reaction model і правила

`ReviewReaction`: `id`, `review`, `user`, `type` (`like` або `dislike`), `created_at`, `updated_at`.

- Unique constraint на `(review, user)`: не більше однієї активної реакції на відгук від одного користувача.
- `PUT` створює реакцію або змінює `type`, якщо реакція вже є. Повторний PUT з поточним значенням ідемпотентний.
- `DELETE` прибирає реакцію поточного користувача; відсутня реакція не є помилкою.
- Реакція на власний відгук дозволена.
- Лічильники `likes_count` та `dislikes_count` обчислюються по реакціях через ORM і не зберігаються в `Review`.
- Голосування не впливає на рейтинг чи popularity локації. Воно не інвалідує list cache локацій, якщо рейтинг/популярність у результаті не змінюються.
- Коли відгук soft-deleted, його реакції зберігаються для історії, а reaction endpoint для видаленого відгуку повертає `404`.
- Коли review редагується через replacement record, старі реакції залишаються пов'язаними зі старим review; новий відгук починає з нульовими реакціями. Це не переноситься автоматично.

## 9. `subscriptions` — підписки на локації

### 9.1. Модель

`LocationSubscription`: `id`, `location`, `user`, `is_active`, `created_at`, `updated_at`, `unsubscribed_at` nullable. Unique constraint на `(location, user)`: один запис підписки на користувача та локацію; повторна підписка реактивує наявний запис замість дублювання.

### 9.2. Функціональні вимоги

| ID | Вимога | Критерій приймання |
|---|---|---|
| FR-SUB-01 | Автентифікований користувач може підписатися. | `PUT` створює підписку або реактивує існуючу. Повторний запит ідемпотентний. Підписатися на власну локацію дозволено. |
| FR-SUB-02 | Користувач може перевірити власний стан. | `GET` повертає лише стан підписки поточного користувача; не розкриває список підписників. |
| FR-SUB-03 | Відписка. | `DELETE` встановлює `is_active=false`, дату відписки, зберігаючи запис. Повторний DELETE ідемпотентний. |
| FR-SUB-04 | Soft Delete локації не скасовує підписки. | Підписки залишаються активними в даних, але ніякі листи про локацію не відправляються, доки вона видалена. Після restore оповіщення поновлюються без повторної підписки. |
| FR-SUB-05 | Валідація локації. | Створення/реактивація підписки дозволене лише для існуючої активної локації. Поточну підписку можна вимкнути незалежно від стану локації, щоб користувач міг керувати власними підписками. |
| FR-SUB-06 | Приватність. | Немає публічного endpoint для переліку підписників; чужу підписку неможливо прочитати/змінити через ID. |

Endpoints: `GET/PUT/DELETE /api/v1/locations/{location_id}/subscription/` (деталі в таблиці app `locations`). У відповіді не виводити email інших користувачів.

## 10. `notifications` — email і transactional outbox

### 10.1. Події та адресати

- Після **першого POST, який створює новий відгук**, лист надсилається автору локації та всім активним підписникам цієї локації.
- Кожен адресат отримує індивідуальний лист, а не CC/BCC-лист зі списком інших одержувачів.
- Якщо автор локації одночасно є підписником, він отримує один лист на одну подію, не дубльований через два джерела включення.
- Сам автор відгуку не виключається з розсилки, якщо входить до множини одержувачів. Власні відгуки дозволені, тому author notification може бути адресований review author у ролі location owner.
- PATCH, що семантично редагує існуючий відгук шляхом Soft Delete + нового record, **не** надсилає повторне email-сповіщення: це редагування, а не нова дія користувача POST.
- Якщо локація Soft Deleted, новий відгук створити не можна, отже лист не ставиться в чергу. Підписки зберігаються після restore.

### 10.2. Надійність доставки

Використовувати Celery + Redis; для надійності — transactional outbox у PostgreSQL:

- `EmailDelivery` зберігає подію доставки щонайменше з `id`, `review`, `recipient user`, `recipient_email_snapshot`, `status` (`pending`, `sent`, `failed`), `attempts`, `last_error` (санітизований текст), `created_at`, `sent_at`.
- Unique constraint на `(review, recipient user)` запобігає створенню двох логічних delivery для того самого адресата/відгуку.
- Outbox rows створюються у тій самій транзакції, що й новий відгук. Після commit завдання можуть одразу публікуватися у Celery.
- Celery Beat періодично сканує pending rows і повторно ставить їх у чергу, якщо enqueue зламався після DB commit. Початковий період sweep — 60 секунд.
- Worker перевіряє статус перед надсиланням; успішна доставка позначається `sent`. Для тимчасових помилок — до 5 спроб із exponential backoff та jitter; після вичерпання — `failed`, причина зберігається без секретів/повного листа.
- Не стверджувати абсолютне exactly-once для SMTP: при збої між прийняттям листа сервером і фіксацією `sent` теоретично можлива повторна доставка. Реалізація має гарантувати унікальний логічний запис і мінімізувати дублікати.
- Помилка email не відкочує вже створений відгук. Вона не повинна робити API request залежним від доступності SMTP.
- Не логувати вміст паролів/токенів; логувати delivery ID, review ID, recipient user ID, спробу та клас помилки.

### 10.3. Endpoints

Публічні API endpoint-и для керування delivery не потрібні. Користувач керує підпискою через subscription endpoint. Стан доставки доступний усередині адмінської діагностики, але окремий публічний endpoint не створюється.

### 10.4. Локальний email

- У development листи відправляються через MailHog SMTP; вебінтерфейс MailHog — лише в локальному профілі.
- У production SMTP host, port, TLS, username/password, sender address задаються тільки environment secrets.
- Застосунок має підтримувати різні email backends через налаштування, а не зашивати MailHog у бізнес-код.

## 11. Redis cache і узгодженість

### 11.1. Обсяг кешування

- Кешувати тільки публічний `GET /api/v1/locations/` результат після застосування пошуку, фільтрів, sorting і pagination; cache key має враховувати normalized query parameters, версію API та generation/version ключ.
- Не кешувати персональні дані, session endpoints, auth responses, реакції поточного користувача або subscription state.
- Detail endpoint, Deleted list і export за замовчуванням не кешуються.
- Default TTL — 60 секунд; TTL конфігурується через `LOCATION_LIST_CACHE_TTL_SECONDS`.
- У cache value входять лише дані відповіді публічного list endpoint, включно з metadata пагінації, рейтингом і popularity. Не кешувати QuerySet object або pickle моделей.

### 11.2. Інвалідація

- Для запобігання масовому пошуку та видаленню всіх key-ів використовувати generation/version key для списків. Після commit релевантної зміни generation збільшується, і всі попередні cache key стають недоступними.
- Інвалідувати після: створення/зміни/Soft Delete/restore локації; зміни назви категорії; створення, редагування/replacement або Soft Delete відгуку.
- Перегляд впливає на popularity, але generation **не** збільшується на кожне нове view, щоб популярна локація не знищувала hit rate кешу. Максимальний відставний час list popularity після нового перегляду — TTL, тобто за default не більше 60 секунд. Detail response використовує актуальні дані без list cache.
- Реакція не інвалідує location list cache, бо вона не входить у popularity/рейтинг.
- Інвалідація виконується тільки після commit; помилка cache не повинна призводити до відкоту основної DB-транзакції. Якщо Redis/cache тимчасово недоступний, list endpoint читає з БД напряму та журналює проблему.
- Redis cache namespace має включати app/version, щоб не змішувати ключі між dev/test/production.
- Для cache keys використовувати канонічно відсортоване представлення query parameters; однаковий логічний запит не має створювати різні keys лише через порядок параметрів.

### 11.3. Відокремлення Redis призначень

Використовувати окремі logical DBs або чіткі namespaces для Django cache, view cooldown keys і Celery broker. `FLUSHDB`/`FLUSHALL` не є допустимою звичайною операцією очищення кешу, оскільки може видалити Celery messages. У production Redis broker не повинен використовувати eviction policy, що випадково видаляє queued tasks; Redis URLs і політики налаштовуються середовищем.

## 13. Нефункціональні вимоги (NFR)

### 13.1. Безпека

| ID | Вимога | Перевірка / критерій |
|---|---|---|
| NFR-SEC-01 | Session + cookies, без JWT. | У залежностях і API flow немає JWT login/refresh endpoint-ів; звичайна автентифікація тримається на Django session cookie. |
| NFR-SEC-02 | CSRF захист. | Небезпечні session-auth запити без/з неправильним token відхиляються; login endpoint також покритий CSRF-тестом. |
| NFR-SEC-03 | Production fail-closed. | `DEBUG=False`; `SECRET_KEY`, `ALLOWED_HOSTS`, DB і broker/email конфігурація надходять з environment; відсутність обов'язкового значення не призводить до запуску з dev default. |
| NFR-SEC-04 | Secure cookies. | `HttpOnly`, `SameSite=Lax`; `Secure` увімкнено у production. Domain/origin не wildcard за замовчуванням. |
| NFR-SEC-05 | Паролі й токени. | Використовуються Django password hashers/token utilities; plaintext secrets не зберігаються та не логуються. |
| NFR-SEC-06 | Права на рівні object. | Тестами доведено ізоляцію чужих locations/reviews/subscriptions і обмеження admin role. |
| NFR-SEC-07 | Rate limits. | Login, email confirmation resend і password reset мають настроювані обмеження. Перевищення дає `429`. |
| NFR-SEC-08 | Валідація. | Client input валідується на рівні serializer/form і критичні інваріанти дублюються DB constraints, де це можливо. ORM використовується для запитів, небезпечні SQL string concatenations заборонені. |
| NFR-SEC-09 | Відсутність секретів у репозиторії. | `.env`, credentials, token dumps і реальні production secrets виключені з Git; `.env.example` не містить секретних значень. |
| NFR-SEC-10 | Безпека помилок. | Публічні помилки не містять traceback, SQL, абсолютних шляхів, SMTP credentials або внутрішніх деталей. |

### 13.2. Продуктивність і навантаження — цільова baseline

Оскільки бізнес-навантаження невідоме, це вимірювані цілі першої версії, а не твердження про вже доведену продуктивність. Вимірювати в стандартизованому staging/CI-like середовищі; hardware і методика мають бути зафіксовані, якщо ці числа використовуються як release gate.

| ID | Вимога | Ціль першої версії |
|---|---|---|
| NFR-PERF-01 | Звичайний list/detail API | За dataset 10 000 локацій і 100 000 відгуків, page size 20, 10 одночасних клієнтів: ціль `p95 <= 500 ms` для list/detail без експорту. |
| NFR-PERF-02 | Query count | Немає N+1 запитів на категорії, рейтинг, автора або reactions у лістингах; query count не зростає лінійно з кількістю результатів сторінки. |
| NFR-PERF-03 | Export | Підтримати експорт 10 000 локацій без обов'язкового зберігання всього CSV в оперативній пам'яті; ціль завершення `<= 10 s` у базовому середовищі. |
| NFR-PERF-04 | Cache freshness | Зміни локацій/категорій/відгуків стають видимими у кешованому list після інвалідації після commit; popularity-only зміни від переглядів — не пізніше TTL за замовчуванням 60 секунд. |
| NFR-PERF-05 | Популярність | Умови sorting/filtering реалізуються в SQL; заборонено завантажувати весь список у Python і сортувати/фільтрувати його після ORM. |

Обов'язкові performance/load tests не додаються; NFR-PERF є інженерною ціллю та підлягає ручному/майбутньому вимірюванню, якщо це потрібно.

### 13.3. Надійність і консистентність

| ID | Вимога | Критерій |
|---|---|---|
| NFR-REL-01 | DB integrity. | Унікальність email, username/category name, активного review per user/location, reaction per user/review і subscription per user/location захищена DB constraints. |
| NFR-REL-02 | Atomic review replacement. | Soft Delete старого review і створення нового відбуваються атомарно; при failure старий запис лишається активним. |
| NFR-REL-03 | View cooldown concurrency. | Одночасні GET-и однієї локації одним identity в межах години створюють не більше однієї `LocationView` події. |
| NFR-REL-04 | Durable view history. | 7-day event history зберігається у PostgreSQL незалежно від Redis restart/cache eviction. |
| NFR-REL-05 | Reliable emails. | Transactional outbox + unique delivery rows + retry/backoff; створення review не залежить від доступності SMTP. |
| NFR-REL-06 | Redis is not source of truth. | Видалення/перезапуск Redis не видаляє locations, reviews, reactions, subscriptions, email delivery state або persisted view events. Кеш можна перебудувати. |
| NFR-REL-07 | Cache transaction order. | Cache generation bump запускається через `transaction.on_commit`; rollback не спричиняє очищення для незафіксованих даних. |

### 13.4. Час і локалізація

- Django `USE_TZ=True`; зберігати timestamps у UTC.
- API timestamps серіалізувати в ISO 8601 із timezone (`Z` або `+00:00`).
- 7-day popularity — sliding interval `now_utc - 7 days <= viewed_at <= now_utc`, не календарні дні й не локальна північ.
- `created_at`/`updated_at` для user/location/review/subscription і event timestamps задає сервер.
- Frontend може локалізувати час самостійно; серверна логіка не залежить від timezone браузера.

### 13.5. Супровідність і стиль коду

- Увесь Python-код перевіряється лише Ruff: `ruff check .` і `ruff format --check .`; Ruff включає sorting imports. Початковий baseline: line length 100, target Python 3.13, набір правил E/F/I/UP/B/SIM (конкретний узгоджений конфіг зберігається в `pyproject.toml`).
- Публічні serializers, views, service functions і складні business expressions мають зрозумілі імена та достатні type annotations там, де це додає ясності; окремий mypy не додається.
- Не приховувати бізнес-логіку у model signals. Складені side effects викликати явно у сервісах; signals допускаються лише для технічних випадків з чітко описаними інваріантами.
- Кожна міграція рев'юється; `makemigrations --check --dry-run` у CI має завершуватися успішно.
- Документація API формується автоматично й відповідає реальним serializers/endpoints.

## 14. CI/CD і Git workflow

### 14.1. Гілки

- `main` — захищена базова/release гілка; прямі push/commit заборонені.
- `dev` — спільна гілка інтеграції функціональності.
- Feature branches відгалужуються від `dev`, а зміни інтегруються в `dev` через Pull Request. `dev` інтегрується у `main` через окремий PR.
- Рекомендовано захистити `dev` тим самим способом, що й `main`, щоб не обходити CI/TDD і не інтегрувати неузгоджені зміни.
- Branch protection: вимагати актуальний successful CI для PR; заборонити force-push і видалення `main`/`dev`; PR використовує squash merge, а title — Conventional Commit header. Статуси checks мають бути required.
- Кожна робоча гілка має номер GitHub issue. Шаблон: `<type>/<issue-number>-<kebab-case-description>`, наприклад `feat/12-session-auth` або `test/18-review-constraints`.
- Дозволені branch types: `feat`, `fix`, `refactor`, `perf`, `style`, `test`, `docs`, `build`, `ops`, `chore`. Назва містить додатне число issue та нижньорегістровий kebab-case опис.

### 14.2. Conventional Commits

Дотримуватися формату Gist: `https://gist.github.com/qoomon/5dfcdf8eec66a051ecd85625518cfd13`, з узгодженим розширенням типів. Заголовок:

```text
<type>(<optional-scope>): <description>
```

- Дозволені типи: `feat`, `fix`, `refactor`, `perf`, `style`, `test`, `docs`, `build`, `ops`, `chore`.
- `scope` необов'язковий, lowercase kebab-case, до 20 символів; scope описує область коду, а не issue number. Наприклад `feat(locations): add soft delete`.
- Description обов'язковий, англійською, до 100 символів, починається з нижнього регістру/цифри, наказовий спосіб і present tense, без крапки в кінці.
- Body і footer не вимагаються; не вимагати breaking-change marker або footer.
- Початковий коміт: `chore: initialize project`.
- Підтримувати типові merge/revert повідомлення лише в узгодженому форматі. Основна інтеграція через squash merge, тому PR title має відповідати Conventional Commits.
- Основний опис Gist містить `perf`, `ops`, `chore`, але його приклад regex дозволяє лише `feat|fix|refactor|style|test|docs|build`. Для цього проєкту canonical list — усі 10 типів, перелічені вище; CI і local hooks мають використовувати одну й ту саму політику.

Приклади:

```text
test(reviews): cover duplicate active review
feat(accounts): add email login
fix(locations): prevent duplicate view events
ops(ci): configure postgres and redis services
docs: document api requirements
```

### 14.3. TDD commit discipline

- Для кожної окремої поведінки спочатку пишеться тест і комітиться окремо, наприклад `test(reviews): cover duplicate active review`.
- Наступним комітом додається мінімальна реалізація, наприклад `feat(reviews): enforce one active review`.
- Перший тестовий коміт може бути червоним: це дозволено на локальному feature branch, але Pull Request не може бути merged, поки поточний стан гілки не проходить весь CI.
- Якщо необхідно, окремий рефакторинг — `refactor(...)` — виконується після Green; результат тестів має залишитися успішним.
- Не створювати implementation commit раніше тестового для нової бізнес-поведінки, крім bootstrap/infrastructure, де немає ще реалізованого доменного контракту.

### 14.4. Локальні Git hooks

Початковий milestone роботи над репозиторієм — налаштувати quality gates **до реалізації бізнес-функцій**:

1. Ініціалізувати проєкт/`uv`, Ruff config і базове pytest/Django test setup.
2. Додати `.githooks/commit-msg`, що перевіряє формат Conventional Commit та довжину/type/scope/description.
3. Додати `.githooks/pre-commit`, що запускає `uv run ruff check .` і `uv run ruff format --check .`; стиль блокує створення коміту.
4. Додати `scripts/install-git-hooks.sh`, який встановлює `git config core.hooksPath .githooks`, перевіряє наявність uv і дає інструкцію, якщо залежності ще не встановлено.
5. Тестові команди не запускаються pre-commit hook-ом, щоб Red-коміт TDD був можливий. Тести блокують merge через CI.
6. CI повторює перевірку форматів/лінтингу та commit message, оскільки локальні hooks можна обійти.

### 14.5. GitHub Actions quality pipeline

Workflow запускається на PR у `dev`/`main` і push до відповідних гілок та feature branches. Застосувати concurrency group за workflow + ref з `cancel-in-progress: true`, щоб новий push скасовував застарілий run. У кожному актуальному run перевіряється snapshot `HEAD`, не запускається окремий повний тестовий suite для кожного commit у branch.

Обов'язкові jobs/steps:

1. Checkout і setup Python/uv.
2. Установка залежностей строго з lockfile (`uv sync --locked` або еквівалент).
3. `uv run ruff check .`.
4. `uv run ruff format --check .`.
5. Запуск PostgreSQL і Redis services з health checks.
6. `python manage.py check`.
7. `python manage.py makemigrations --check --dry-run`.
8. Застосування міграцій до тестової БД.
9. `uv run pytest` з unit, API та integration tests.
10. Commit-message validation для всіх commit headers, які вводяться PR у базову гілку; винятки merge/revert — лише ті, що описані в єдиному regex/policy.

- Failed tests або failed required checks блокують merge; відсоток coverage не є required gate.
- Невдалий тест не блокує локальний commit, але обов'язково блокує merge.
- Стиль коду блокує локальний commit і додатково перевіряється в CI.
- Не додавати сторонні code-quality tools поза Ruff без окремого рішення.

## 15. Docker Compose і операційні вимоги

### 15.1. Development Compose

Мінімальні сервіси:

- `web` — Django REST API.
- `db` — PostgreSQL із named volume і healthcheck.
- `redis` — Redis із healthcheck.
- `worker` — Celery worker.
- `beat` — Celery Beat для sweep pending email deliveries.
- `mailhog` — локальний SMTP sink + web UI.

`web`, `worker` і `beat` використовують той самий image/config та відрізняються command. `depends_on` має орієнтуватися на health/readiness, але код також повинен коректно повідомляти про недоступність залежностей. DB volume зберігає дані після `docker compose down`; видалення volume — окрема destructive дія.

### 15.2. Production-ready configuration template

- Окремий `compose.production.yaml` може бути шаблоном/overlay: DEBUG off, application server (не Django development server), required env vars, restart policy, healthcheck, окремий worker/beat, без MailHog.
- Ніяких вигаданих доменів, production secrets або хостів у репозиторії. Якщо production-specific значення не відомі, це обов'язкові environment variables з чіткою помилкою на старті.
- Production secrets подаються через deployment environment/secret manager, а не `.env` у Git.
- Не відкривати PostgreSQL/Redis назовні за замовчуванням; порти доступні лише внутрішній compose network, крім явно дозволених dev ports.

### 15.3. Очікувана інструкція запуску

Після реалізації README має дозволяти розробнику, який має Docker Compose та uv, запустити проєкт однією командою:

```bash
docker compose up --build
```

Після першого старту має бути документовано як застосувати міграції, створити admin user і відкрити Swagger UI. Якщо стартова команда запускає міграції автоматично, це має бути безпечним при повторному виконанні й не підміняти контроль міграцій у CI.

## 16. Вимоги до тестів і acceptance checklist

До завершення реалізації повинні існувати тести щонайменше для наступних сценаріїв:

### Accounts

- Реєстрація валідного користувача, унікальність email/username і недопущення призначення `admin` через payload.
- Непідтверджений користувач не може увійти; валідний токен підтверджує лише відповідний account; token invalid/expired/reused відхиляється.
- Email login створює session; logout інвалідовує її; `/me` працює лише з дійсною сесією.
- CSRF: login/logout і session-auth write endpoints відхиляють відсутній/неправильний token.
- Password reset не розкриває існування email; password validators застосовуються.
- Rate limit повертає `429`.

### Categories

- Public list/detail, admin-only create/update/delete.
- Сase-insensitive unique name.
- Migration створює seed categories.
- Видалення category, яка є в active або soft-deleted location, повертає `409`.

### Locations

- Public active list/detail; create тільки auth; update/delete/restore object permissions owner/admin.
- Серверні author/timestamps неможливо підмінити.
- Required fields, coordinate boundaries, at least one category, multiple category support.
- Soft Delete ховає location зі звичайних read endpoints, зберігає related data; deleted list scope й restore права працюють.
- Після restore data/reviews/reactions/subscriptions/view history збережені.
- Search AND filtering semantics, category repeated filter, username filter, rating/popularity range, ordering tiebreaks, pagination bounds.
- ORM query count не має N+1 для категорій/автора/агрегатів.
- JSON/CSV export застосовує поточні query parameters, не пагінує, включає потрібні поля й CSV перевіряється на валідне escaping; CSV path використовує pandas.

### Reviews/reactions

- Рейтинг тільки 1..5, comment optional and max length.
- Duplicate active review returns `409` навіть за concurrent POST.
- Self-review дозволено; автор не може редагувати чужий review, включно з admin.
- Replacement update transactionally soft-deletes previous active review and creates new active record.
- Delete is soft; deleted reviews виключені з list/rating/counts.
- Like/dislike create, switch, GET own state, DELETE idempotency, unique `(review,user)`, self-vote allowed.
- Reaction counts are calculated and separate; they do not change popularity.

### Views/popularity/cache

- Successful location detail adds one view event; invalid/deleted/detail failure/list/export does not.
- Same identity+location within 60 minutes does not add another event; another location has independent cooldown.
- Concurrent requests do not double count; Redis restart does not lose persisted history.
- `V7` uses rolling seven days UTC and excludes older events.
- Average review rating uses active reviews only, rounded to one decimal; no reviews -> `null`.
- Popularity formula exact weights/constants/rounding; no stored derived columns; DB query can sort/filter it.
- Location/review/category writes invalidate cache after commit; rollback does not invalidate; view changes appear after cache TTL.
- Cache outage safely falls back to database without returning private/stale incompatible data.

### Subscriptions/email

- Subscription create/reactivate/GET-own-status/unsubscribe; one row per user/location.
- Soft Delete pauses notification sends but keeps subscription; restore resumes.
- New review creates one logical delivery per unique recipient (owner plus active subscribers); overlapping roles produce one mail; review PATCH does not notify.
- Celery task retry/backoff/max attempts and final failure status are tested; email error does not roll back review; MailHog used only in development.
- Pending outbox delivery remains discoverable after broker enqueue failure; beat sweep re-enqueues.

### Infrastructure/CI

- `docker compose up --build` starts required local services.
- Migrations work on clean DB; Django system checks and migration drift check pass.
- `uv.lock` tracks exact dependencies; `uv sync --locked` succeeds.
- Ruff lint and format pass; invalid commit message/style is blocked locally; CI duplicates checks.
- Test failure blocks merge; test-only Red commit is possible locally.
- Swagger schema covers all public API endpoints.

## 17. Definition of Done

Feature вважається завершеною лише коли:

1. Є узгоджений тест, який визначає очікувану поведінку.
2. Реалізація проходить відповідний unit/API/integration test.
3. Немає неочікуваного порушення access control, DB constraints, cache invalidation або transaction boundary.
4. `ruff check .`, `ruff format --check .`, `manage.py check`, `makemigrations --check --dry-run` і тестовий suite проходять на поточному стані гілки.
5. Документація OpenAPI відповідає endpoint/serializer поведінці.
6. Зміни не включають секрети, випадковий рефакторинг поза задачею або недокументовані залежності.
7. Назви гілки й комітів відповідають правилам; тестовий коміт створено перед реалізаційним для нового бізнес-правила.
8. PR може бути merged лише після успішного CI на актуальному HEAD.

## 18. Рішення, зафіксовані в цій версії

Цей документ фіксує конкретні значення, щоб уникнути різних трактувань під час реалізації:

- Rating: average of active reviews, all time, one decimal; no active reviews -> `null`.
- Popularity: formula in §7.4; two decimals, 0–100; all time reviews/rating, rolling 7-day views.
- Sorting default: popularity descending, then rating descending, views descending, name ascending, id ascending.
- Listing pagination: page-number, default 20, max 100.
- Location fields: name 150, description 5,000, address 255; coordinates 6 decimal places with geographic boundaries.
- Review: rating 1–5, optional comment max 2,000; edit is a transactionally soft-deleted replacement record.
- Review votes: one current like/dislike per user/review; PUT can change it; DELETE clears it.
- Location list cache: TTL 60 s; transactional generation-based invalidation on location/category/review changes; views are reflected no later than TTL.
- View identity/cooldown: authenticated user ID or anonymous Django session, per location, sliding 60 minutes; view event history durable in PostgreSQL, Redis used for fast cooldown.
- Mail: Celery 5.6 + Redis, PostgreSQL outbox, up to 5 attempts with exponential backoff, Beat sweep every 60 seconds, MailHog in development.
- API base: `/api/v1/`; Swagger `/api/v1/docs/`; schema `/api/v1/schema/`.
- Quality gates first: commit message and Ruff hooks + initial CI/test infrastructure before feature implementation; tests block merge, style blocks commit.
